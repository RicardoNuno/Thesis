# cho2021: Reflect, not Regret: Understanding Regretful Smartphone Use with App Feature-Level Analysis

**Authors / venue / year:** Cho, Choi, Kim, Kang, Choe & Lee / Proceedings of the ACM on Human-Computer Interaction 5(CSCW2), Article 456, 36 pp. / 2021 (CSCW 2021 Best Paper)
**Link:** https://doi.org/10.1145/3479600
**Relevance:** high

## Summary (3 sentences)

To keep engagement, app providers ship many features in one "super app", mixing utilitarian and hedonic features (e.g. Facebook search vs recommended videos), so app-level screen time or limits cannot tell wanted from unwanted use. The authors built Finesse, an Android tool that logs which feature of Instagram, Facebook, YouTube and KakaoTalk is in use and, right after a session, asks which feature uses the user regrets; 29 students used it for a week, followed by interviews. Regret comes from three patterns: habitual checking of "following" content once it is depleted, a habitual feature tour / sidetracking into recommended content placed next to instrumental features, and the "just a bit more" rabbit hole of recommended bite-sized content.

## Method

- N = 29 Android users in Korea (15 F, 14 M; age 19–27, M 21.97), 28 students; recruited via university forums; daily use of ≥ 3 of the 4 apps.
- Finesse: Android Accessibility API reads the UI tree on scroll/click/focus; tab selected, layout, class names, window ID and hashed text identify 43 features (by user action × content form × source: own / following / recommended). Unknown layouts → "undefined". Text only kept hashed (privacy).
- Session = app open until home screen, app switch via notification, or lock.
- ESM: after a sampled session, overlay shows a timeline of the features used; user taps the ones they regret. Dismissed after 5 min so only immediate regret counts. Sampling balanced by app, session length (< 30 s, 30 s–5 min, ≥ 5 min) and eight 3-hour bins, 50% chance, sessions < 5 s skipped.
- 1-hour retrospective interview with a dashboard of regretted uses and weekly feature-level usage.
- Regret framed with regret theory (Loomes & Sugden): regret when the best alternative reward exceeds the actual reward of the use.
- Analysis: feature use probability, feature regret ratio, GLMM (feature fixed, participant random; baseline = each app's entry feature), in-session time bins; thematic analysis of interviews.

## Results / evidence

- 18,263 sessions (90.0/person/day; KakaoTalk 51.6, Instagram 17.4, YouTube 11.7, Facebook 10.7). 4,246 prompts, 4,069 answered (95.8%).
- 26.5% of answered sessions had ≥ 1 regretted feature: Instagram 41.9%, Facebook 33.2%, YouTube 22.0%, KakaoTalk 18.1%. Of these, 60% partially and 40% fully regretful → experience varies within an app.
- Active features (chat, search, upload, DM) are regretted less than passive viewing features (feeds, stories, recommended videos, KakaoTalk NEWS). KakaoTalk NEWS 2.83× more likely regretted than CHAT.
- Same reward, different presentation → different regret: Instagram VIEW_STORY regretted more than FOLLOWING_POSTS (ephemeral stories create an urge to "just press it").
- Four rewards of use: social, informational, personal interests, entertainment. Alternative rewards: productivity, sleep / physical condition, social relationships (e.g. phone at a meal).
- Habitual checking is regretted when it repeats and delivers no new content, i.e. no reward; mostly with subscription-based features, regretted early in sessions.
- Feature tour / sidetracking: after an empty check or after an instrumental task (e.g. reading a chat), users drift into recommended features; regret because intended rewards are delayed and time cost grows.
- Rabbit hole: recommendation-based features dominate regret in sessions > 10 min.
- Participants valued feature-level usage reports over app-level ones: shows necessary vs unnecessary time, prevents self-justification ("it includes messaging"), and gives an actionable target.
- Why regretful use repeats: delay discounting / impulsive choice (smaller, sooner reward over larger, later one), helped by dark patterns and the variable reward schedule of recommendations.

## Strengths / limitations

- Strength: logged, feature-level data paired with in-situ ESM, not self-reported totals; high response rate (95.8%).
- Strength: theory-grounded construct (regret theory, delay discounting) and concrete design implications.
- Strength: reviews interventions: restrictive ones (MyTime timeout, PomodoLock, GoalKeeper, LocknType, Lock n' LoL, NUGU) work but frustrate users because they ignore context; non-restrictive ones (screen time, visit counts) are too coarse for multi-feature apps.
- Limitation: binary regret question; no context collected in the ESM (recovered only in interviews); only immediate regret (may change hours later).
- Limitation: 29 students at a top Korean university, one week, 4 apps, Android only; likely biased to productivity-driven regret.
- Limitation: rule-based feature detection is fragile to app updates; sampling policy may bias which sessions were rated.
- Limitation: Fig. 4 caption reads GLMM estimates as "times more likely", but the values (e.g. −13) look like log-odds, so the ratios are unclear.

## How it relates to my thesis

Regret is a usable signal for an intervention: it marks use that failed to deliver a reward, which ties to the reinforcement view (skinner1948) and to the checking habit (oulasvirta2012, heitmayer2021): a check that finds nothing new is exactly the case people regret. Supports a non-restrictive design, since blocking frustrates users; their design implications map directly onto my thesis: (a) show expected rewards before opening ("content x% charged"), (b) show the prospective cost (how long this will likely take) rather than time already spent, (c) remind of alternatives ("What were you going to do after this?"), triggered only when a pattern is detected (e.g. > 5 min or 10 items in a recommended feed). Also argues that logging should go below the app level, and Finesse shows it is feasible on Android with the Accessibility API, which matters for my Android monitoring comparison. The post-session ESM prompt is itself a light reflection intervention.
